## 发布状态

**v0.1.0-rc.2 是预发布，不是生产稳定版。** 它替代已撤下的服务端 rc.1，并重新整理了代码历史。SDK 的已发布版本没有改写。

你可以用它评估功能，但需要在自己的环境完成容量、恢复和安全验证，再决定是否上线。通过构建或功能测试，不代表已经达到某个吞吐量，也不构成可用性保证。

[当前生产验收清单](https://github.com/viber-ops/configra/blob/v0.1.0-rc.2/docs/production-readiness.md)列出了尚未完成的工作。[历史验证记录](https://github.com/viber-ops/configra/blob/v0.1.0-rc.2/docs/verification/2026-09-12.md)注明了每次测试的版本和范围，不应直接当作新版本的全部验收结果。

## 谁能读取哪些数据

- **Token 按环境授权。** 获得 `production` 权限的应用，可以读取该环境中的所有 Config 和 Vault 值，不能只授权某个条目。
- **Namespace 只是分组。** Vault Namespace 和 Kubernetes Namespace 都不能缩小 Token 在 Configra 服务端的权限。
- **网页角色覆盖整个工作区。** Admin 可以管理数据；Viewer 只读，并且不能查看敏感值。它们不是按项目分配的角色。

如果两个团队或应用不能互相读取数据，不要把它们放进同一个环境再靠命名区分。应使用独立部署，或选择具备所需权限粒度的方案。

## 已有的保护及其限制

应用读取使用 HTTPS，默认同时检查 Token 和客户端证书。网页登录交给配置的登录系统，管理操作检查 Admin 权限。

Vault 值和 CA 签名私钥加密保存在数据库中。但如果攻击者同时拿到数据库和 Master Key，仍可能解密这些内容，所以必须分开控制访问和备份。客户端私钥只在首次签发时交付，服务端不保留。

吊销 Token、客户端证书或 CA 后，会阻止后续授权读取，**不会删除应用已经下载的配置**，也不会清空已经同步的 Kubernetes Secret。

Kubernetes CSI provider 是运行在节点上的受信任组件；同步控制器具有所在应用命名空间的 Secret 读写权限。安装前需要确认你愿意授予这些权限。

## 当前还不能保证什么

| 事项 | 对使用者的影响 |
| --- | --- |
| 每秒 1000 次读取的持续负载 | 当前要求的十分钟验收尚未通过，不能按这个数字规划生产容量 |
| 大量配置和条目的列表查询 | 部分后端接口仍返回完整集合；网页分页不代表数据库只查询一页 |
| 自动轮换 Master Key | 没有自动轮换，也没有 HSM / KMS 硬件或云密钥托管 |
| 按单条配置授权 | 当前权限粒度仍是整个环境 |
| 自动重启应用 | 修改配置后，需要应用自己的重载逻辑，或由部署系统重启 |
| 自动部署续期证书 | 可以签发新证书，但替换应用中的旧证书和到期告警需要另行安排 |

## 访问日志与审计日志

Access 记录读取操作，通过 NATS 发送；故障时可能丢失，不能作为“每次读取都有记录”的保证。

Audit 记录变更操作。已保存的审计事件通过数据库待发送队列重试投递。rc.2 修复了客户端证书事件的解码问题，并为已登录用户的写入拒绝增加记录。如果记录无法持久化，请求会返回 `503 audit_unavailable`。数据库不可用时不能承诺仍然保存了记录；大规模故障恢复还需要继续验证。

## 怎样反馈问题

普通使用问题可以[提交 Issue](https://github.com/viber-ops/configra/issues)。请提供版本、状态码、Request ID 和脱敏后的最小复现，不要附上 Token、私钥、生产配置或完整敏感响应。

安全漏洞请使用仓库的[私密报告入口](https://github.com/viber-ops/configra/security/advisories/new)，不要先公开利用细节。
